# Elixir/Rust 言語学習のための固定題材 仕様書（バッチ処理編）

Elixir・Rust の言語仕様を勉強するために、Webアプリではなくバッチ処理から入るための3題材の仕様。リリースはしない。目的は「その言語らしい書き方・特徴が出る部分に触れること」であり、プロダクトとしての完成度ではない。

## 使い方

1. **単語頻度カウントバッチ** … 最初に必ずやる基礎文法の足慣らし。コレクション操作・パターンマッチ／match式・文字列処理・ソートを一通り触る。
2. **並行データ収集バッチ** … 基礎文法に慣れたら次に。並行処理・部分失敗耐性・リトライ／タイムアウトが心臓部。今後Web API化しやすい汎用題材。
3. **大量ログのストリームETL** … 並行処理と並行して、または後に。メモリに載らない前提でのストリーム処理・遅延評価が心臓部。

同じ題材をElixirとRustの両方で実装し、書き味の違いを比較すること自体が学習の主目的。

各題材の最後に「評価チェックリスト」を置いてある。実装後にこれを埋めると、言語間の比較メモとして蓄積できる。

---

# 題材1: 単語頻度カウントバッチ（入門）

## 目的

並行処理やストリームなどの応用に入る前に、コレクション操作・パターンマッチ／match式・文字列処理・ソートといった言語の基本文法を一通り触る。あくまで文法の足慣らしであり、拡張は行わない。

## 入力

適当なテキストファイル（英語または日本語の分かち書き済みテキスト、数千〜数万語程度）。自作の生成スクリプトで用意してよい。

## 処理フロー

1. テキストファイルを読み込む
2. 単語に分割し、正規化する（小文字化、記号除去など）
3. 単語ごとの出現回数を集計する（辞書／マップ構造を使う）
4. 出現回数の多い順にソートして上位N件を出力する
5. ストップワード（"the", "a" など）を除外するオプションを付ける

## 機能仕様

- CLI引数で入力ファイルパスを指定できる
- CLI引数で「上位N件」（デフォルト10）を指定できる
- CLI引数で「ストップワード除外の有無」を切り替えられる
- 結果は「単語, 出現回数」の形式で標準出力に表示する
- 空ファイル・存在しないファイルパスを渡した場合はエラーメッセージを出して異常終了する

## 見るポイント

- Elixir: パイプ演算子（`|>`）でのデータ変換チェーン、`Enum.reduce`によるMap構築、パターンマッチでのタプル分解
- Rust: `HashMap` の使い方、`Vec`のソート（`sort_by_key`）、`Option`/`iter()`チェーン、所有権のごく基礎（`String` vs `&str`）

## やらないこと

- 並行処理
- ストリーム処理（ファイル全体をメモリに載せてよい）
- 多言語対応の高度な形態素解析（空白区切り程度でよい。日本語を使う場合は簡易分かち書き済みのものを用意する）
- 拡張機能全般（この題材は次の2題材への準備運動として固定のまま使う）

## 完了の定義

数千語規模のテキストファイルを渡し、上位10件の単語と出現回数が正しく表示されること。ストップワード除外オプションのON/OFFで結果が変わることを確認できること。

## 評価チェックリスト

- [ ] Map/HashMap相当のデータ構造の扱いは直感的だったか
- [ ] コレクションのソート・フィルタ・変換のチェーンは読みやすく書けたか
- [ ] 文字列の正規化（大小文字・記号除去）は標準ライブラリで完結したか
- [ ] エラー時（ファイル不在など）のハンドリングはどう書いたか（例外/Result/エラータプルなど）
- [ ] CLI引数のパースは標準機能で足りたか、ライブラリが要ったか

# 題材2: 並行データ収集バッチ

## 目的

複数ソースからの並行取得・部分失敗耐性・リトライ／タイムアウトを両言語で扱う。並行処理モデルの違い（Elixirの軽量プロセス vs Rustのasync/タスク）が最もよく表れる題材で、今後Web API化や実データへの差し替えにも転用しやすい。

## 入力

取得対象URLのリスト（設定ファイルまたは引数、5〜20件程度）。学習用に疑似APIとして自前のモックHTTPサーバーを立てて使う（正常応答・遅延応答・エラー応答・タイムアウトの4パターンを返せるようにしておく）。

## 処理フロー

1. 対象リストを読み込む
2. 各ソースに対して並行にHTTPリクエストを発行する（最大同時実行数を制限できること）
3. 各リクエストにタイムアウトを設定し、失敗時は指数バックオフで最大N回リトライする
4. 全ソース分の処理が終わるまで待ち合わせる（一部失敗しても他は継続する）
5. 成功分のレスポンスをパースして共通スキーマに正規化する
6. 結果をCSVまたはJSONにまとめて出力する
7. 標準出力かログに「成功件数／失敗件数／各ソースの所要時間」のサマリを出す

## 満たすべき要件

- 最大同時実行数の制御ができる（無制限に並行させない）
- 1件の失敗が全体を止めない
- リトライとタイムアウトの挙動を意図的にテストできる（わざと失敗するモックエンドポイントを用意する）
- 終了コードで「全部成功／一部失敗／全滅」を区別する

## データモデル（正規化後のレコード）

```
FetchResult(source_url, status, body_summary, duration_ms, attempt_count, error_reason?)
```

## 言語特徴の見せ場

- Elixir: `Task.async_stream(max_concurrency: N)` による並行制御、Supervisor配下での再起動戦略（let it crash）、パターンマッチによるレスポンス分岐
- Rust: `tokio::task::JoinSet` や `futures::stream::buffer_unordered` による並行制御、`Result<T, E>` の連鎖とカスタムエラー型（`thiserror`等）、所有権を意識した非同期タスクへのデータ受け渡し

## やらないこと

- 実際の外部本番APIへの依存（学習中は自前のモックサーバーで完結させる）
- 分散実行（複数マシンにまたがる並行処理）
- 認証が必要な複雑なAPI連携

## 完了の定義

- 20件中数件がタイムアウト・エラーを返すモック構成で実行し、成功分のみが正しく集計・出力されること
- 最大同時実行数を変えると実行時間が変わることを確認できること
- リトライ回数・バックオフの挙動をログで確認できること

## 評価チェックリスト

- [ ] 並行実行数の制御はどのAPIで行ったか、直感的だったか
- [ ] 1件の失敗が他のタスクに波及しない設計はどう書いたか
- [ ] リトライ・バックオフのロジックは自前実装かライブラリ利用か
- [ ] タイムアウトの表現（例外/Result/メッセージ）は言語として自然だったか
- [ ] 全タスクの完了待ち合わせと結果集約はどう書いたか（構造化並行性の有無）
- [ ] エラー型の設計（成功/失敗/部分失敗をどう表現したか）

## 拡張案（発展として、この仕様書の対象外）

取得先を実際のAPI（為替レートや天気など）に差し替えてWeb API化、定期実行化（cron/GenServer timerなど）

# 題材3: 大量ログのストリームETL

## 目的

メモリに乗り切らない前提でのストリーム処理・遅延評価・パース失敗のスキップ耐性を扱う。イテレータ／Streamという抽象化の違いが最もよく表れる題材。

## 入力

自作の生成スクリプトで作った大きめ（数十万行〜）のアクセスログ／CSV。意図的に一部不正な行（カラム欠落・不正フォーマット）を混ぜておく。

## 処理フロー

1. ファイルを一括ロードせず1行ずつストリームで読み込む
2. 各行をパースして構造化データに変換する（不正な行はスキップしてエラーカウントに計上し、処理は止めない）
3. 集計処理を行う（例: エンドポイント別アクセス数、ステータスコード別件数、時間帯別集計など複数軸を同時に）
4. 集計結果をCSV/JSONで出力する
5. 最後に「総行数／正常処理件数／スキップ件数／処理時間」のレポートを出す

## 満たすべき要件

- ファイル全体を一度にメモリへ展開しない（ストリーム/イテレータで処理する設計にする）
- 不正行があっても処理全体は継続する
- 集計は複数軸を同時に行う（単一カウンタで済ませない）
- 巨大ファイルでもメモリ使用量が一定に近いことを確認できる（実行時にメモリ使用量を計測する）

## ログのフォーマット例（CSV）

```
timestamp,method,path,status,response_ms
2026-07-24T10:00:00Z,GET,/api/users,200,42
2026-07-24T10:00:01Z,POST,/api/orders,500,301
（一部の行はカラム欠落・不正な値を意図的に混入させる）
```

## 言語特徴の見せ場

- Elixir: `Stream` モジュールによる遅延評価（`Enum`で書いた場合とのメモリ差を体感する）、`File.stream!/1`
- Rust: `Iterator` の遅延評価とゼロコスト抽象化、`BufReader` による行読み込み、所有権を意識したパース処理（不要なコピーを避ける設計）

## やらないこと

- リアルタイムのログ監視（tail -f的な継続処理）
- 分散処理・複数ファイルの並行読み込み（題材2との差別化のため、この題材では単一ファイル・単一スレッド前提のストリーム処理に集中する）
- DBへの書き込み

## 完了の定義

- 数十万行規模のログファイルを処理し、複数軸の集計結果が正しく出力されること
- 不正行を意図的に含めても処理が止まらず、スキップ件数がレポートに正しく反映されること
- `Enum`/一括ロードで書いた場合との比較で、ストリーム実装の方がメモリ使用量が低く抑えられることを確認できること

## 評価チェックリスト

- [ ] ストリーム/イテレータの遅延評価は体感できたか（一括ロード版とのメモリ差を計測できたか）
- [ ] 不正行のスキップとエラー集計はどう表現したか
- [ ] 複数軸の集計をどうデータ構造として設計したか
- [ ] ファイル読み込みのバッファリング（行単位読み込み）は標準ライブラリで素直に書けたか
- [ ] 所有権/借用を意識したパース処理でコピーを避けられたか（Rust）／不変データ前提での集計更新はどう書いたか（Elixir）

## 拡張案（発展として、この仕様書の対象外）

集計結果をDBに書き込む、監視ダッシュボード用のAPIとして常駐化する

# 付録: 比較メモの残し方

言語ごとに1ファイル、以下の形式でメモを残すと後で比較しやすい:

```
# <言語名> <バージョン> (試用日)

## 実施した題材と所要時間
## 評価チェックリスト結果（上記のコピー）
## 感動した点 / 苦しんだ点（各3つまで）
## 並行処理モデルの所感（題材2）
## ストリーム/イテレータの所感（題材3）
## 生成AIとの相性（ドキュメント・エコシステムの学習しやすさ）
```
