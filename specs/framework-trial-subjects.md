# フレームワーク試用のための固定題材 仕様書

新しいウェブフレームワークを評価するときに毎回使い回すための、3つの題材の仕様。リリースはしない。目的は「フレームワークの強み・弱み・設計思想に触れること」であり、プロダクトとしての完成度ではない。

## 使い方

1. **RealWorld＋拡張** … 最初に必ずやる基礎体力測定。フルスタック/フロント/バックエンドを問わず共通。
2. **予約カレンダー** … バックエンド寄りのフレームワーク（Rails, Laravel, Phoenix, NestJS など）に興味を持ったら深掘り用に。
3. **リアルタイムクイズ** … フロントエンド寄りのフレームワーク（React系, Svelte, Solid, Vue など）に興味を持ったら深掘り用に。

Next.js / Nuxt / SvelteKit のようなフルスタック系は、試したい側面に応じて 2 か 3（または両方）。

各題材の最後に「評価チェックリスト」を置いてある。実装後にこれを埋めると、フレームワーク間の比較メモとして蓄積できる。

# 題材1: RealWorld＋拡張

## 目的

RealWorld（Conduit）の公式仕様をベースに、CRUDでは見えない領域をカバーする拡張を固定で追加したもの。ルーティング・認証・フォーム・データ取得・リレーションという「どのフレームワークでも必ず書く部分」の書き味を測る。

ベース仕様: https://realworld-docs.netlify.app/ （Medium風ブログ）

## ベース部分（RealWorld公式仕様のまま）

- ユーザー登録・ログイン（JWT）
- プロフィール表示・編集、ユーザーのフォロー/アンフォロー
- 記事のCRUD（Markdown本文、slugベースのURL）
- 記事へのコメント追加・削除
- 記事のお気に入り（いいね）
- タグ付け、タグによる絞り込み
- フィード（グローバル / フォロー中ユーザーのみ）
- ページネーション（オフセット方式で可）

公式のAPI仕様・画面仕様が存在するので、詳細はそちらに従う。既存実装が多数公開されているため、書き終えたら他人の実装と比較すること。

## 拡張仕様（毎回必ず実装する）

### 拡張A: 記事サムネイル画像のアップロード

- 記事作成・編集画面で画像を1枚アップロードできる
- 保存先はローカルファイルシステムでよい（S3等は不要）
- 一覧・詳細でサムネイル表示。未設定ならプレースホルダー
- 制約: 5MB上限、jpeg/png/webpのみ。違反時はフォームエラーとして表示
- **見るポイント**: multipart処理の作法、ファイルバリデーション、静的ファイル配信の設定、フォームとの統合

### 拡張B: 管理者ロール

- ユーザーに `admin` フラグを持たせる（付与はDB直接操作 or seedでよい。管理画面は作らない）
- adminは任意の記事・コメントを削除できる
- adminのみアクセスできる「通報一覧」ページを1枚追加（通報機能自体は「記事詳細に通報ボタン→理由をテキストで送信」だけの最小実装）
- 非adminがアクセスしたら403
- **見るポイント**: 認可のレイヤー（ミドルウェア? ガード? ポリシー?）、ルート保護の宣言方法、UIの出し分け

### 拡張C: 記事検索＋キャッシュ

- タイトル・本文に対するキーワード検索（LIKE検索でよい。全文検索エンジンは不要）
- 検索結果ページはURLにクエリを反映（`/search?q=...`）し、リロード・共有可能にする
- グローバルフィードの1ページ目に60秒キャッシュをかける（方式はフレームワークの流儀に従う: HTTPキャッシュ、データキャッシュ、メモ化、なんでもよい。「そのフレームワークならどうやるのが自然か」を調べること自体が目的）
- **見るポイント**: URLと状態の同期、データ取得層のキャッシュ戦略、キャッシュ無効化の考え方

## データモデル

```
User(id, username, email, password_hash, bio, image, is_admin)
Article(id, slug, title, description, body, thumbnail_path, author_id, created_at, updated_at)
Comment(id, body, article_id, author_id, created_at)
Tag(id, name) / ArticleTag(article_id, tag_id)
Favorite(user_id, article_id)
Follow(follower_id, followee_id)
Report(id, article_id, reporter_id, reason, created_at)
```

## やらないこと

- メール送信、パスワードリセット
- 画像のリサイズ・最適化
- 全文検索エンジン（Elasticsearch等）
- 本番デプロイ、CI/CD
- レスポンシブ対応の作り込み（崩れていなければよい）

## 完了の定義

ユーザー2人（うち1人admin）で、登録→記事投稿（画像付き）→フォロー→フィード確認→コメント→通報→adminで削除、が一通り通ること。

## 評価チェックリスト

- [ ] ルーティング（動的セグメント、ネスト）は宣言的に書けたか
- [ ] 認証状態の保持と伝播（サーバー/クライアント間）は素直だったか
- [ ] フォームのバリデーションエラー表示に定型パターンがあるか
- [ ] ORMまたはデータ層でN+1に気づける仕組みがあるか
- [ ] ファイルアップロードは公式ドキュメントだけで実装できたか
- [ ] 認可（拡張B）はフレームワークの機能で書けたか、自前実装になったか
- [ ] キャッシュ（拡張C）の「流儀」は明確だったか、選択肢が多すぎて迷ったか
- [ ] 公開されている他者のRealWorld実装と比べて、自分のコードは慣用的だったか

# 題材2: 予約カレンダー（バックエンド深掘り用）

## 目的

「会議室予約」を題材に、排他制御・時刻処理・状態遷移・バックグラウンドジョブという、CRUDには現れないバックエンドの核心を測る。フロントは最低限でよく、サーバー側の設計に時間を使う。

## 登場する概念

- **リソース**: 予約対象（会議室）。名前と営業時間（例: 平日9:00–18:00）を持つ。3件程度をseedで用意し、管理画面は作らない
- **予約**: あるリソースの連続した時間帯を1ユーザーが確保したもの
- **予約枠**: 30分単位。予約は連続する枠を1つ以上まとめて取る（例: 10:00–11:30）

## 機能仕様

### F1. 空き状況表示

- リソースごとの週間カレンダー表示（縦=時間帯、横=曜日程度の簡素なグリッドでよい）
- 空き枠 / 自分の予約 / 他人の予約（名前は出さず「予約済み」とだけ）を区別して表示
- 営業時間外はグレーアウト
- 前週・翌週への移動。過去週は閲覧のみ

### F2. 予約の作成

- 空き枠をクリック→開始・終了時刻と用件（テキスト）を入力→確定
- バリデーション:
  - 営業時間内であること
  - 過去の時刻でないこと
  - 最長4時間まで
  - 既存予約と重複しないこと
- **重複チェックはDB層で保証すること**（この題材の心臓部）:
  - アプリ層のチェックだけでなく、トランザクション＋ロック、排他制約（PostgreSQLの `EXCLUDE USING gist` 等）、直列化可能分離レベル、のいずれかで「同時に2リクエストが来ても片方は必ず失敗する」ことを保証する
  - どの手段を選んだか、なぜか、をメモに残す
  - 検証方法: 同一枠への予約リクエストを並行で2本投げるテスト（またはスクリプト）を書き、片方が409相当で落ちることを確認する

### F3. 予約の変更・キャンセル

- 自分の予約のみ変更・キャンセル可能
- 開始時刻の30分前を過ぎたら変更・キャンセル不可（サーバー側で判定）
- 予約は物理削除せず `canceled` 状態にする（状態: `confirmed` → `canceled`）

### F4. タイムゾーン

- DBはUTCで保存、表示はユーザーのタイムゾーンで行う
- ユーザー設定にタイムゾーンを持たせ、切り替えたら表示が変わること（Asia/Tokyo と America/New_York の2つで確認できれば十分）
- **見るポイント**: 標準の日付ライブラリ/エコシステムの質。ここで苦労するかどうかは言語・フレームワークで大きく差が出る

### F5. リマインダー（バックグラウンドジョブ）

- 予約開始の10分前に「リマインダー送信」を行う
- 実際のメールは送らず、`reminders` テーブルへのレコード追加＋ログ出力でよい
- キャンセル済み予約には送らない
- **見るポイント**: ジョブキュー/スケジューラがフレームワークに統合されているか（Rails: ActiveJob, Laravel: Queue+Scheduler, Phoenix: Oban/プロセス）、外部依存（Redis等）が必要か、遅延実行のキャンセルはどう表現するか

### F6. 認証

- 簡素でよい。RealWorldで作った認証方式を流用するか、フレームワーク付属のスキャフォールド（Rails の authentication generator, Laravel Breeze 等）があればそれを使い、スキャフォールドの品質も評価対象とする

## データモデル

```
User(id, name, email, password_hash, timezone)
Room(id, name, open_time, close_time)
Reservation(id, room_id, user_id, starts_at, ends_at, purpose, status, created_at)
  status: confirmed | canceled
Reminder(id, reservation_id, scheduled_at, sent_at)
```

## やらないこと

- 繰り返し予約（毎週火曜など）
- 承認フロー（申請→承認）
- 祝日・休業日の考慮
- 実際のメール送信
- カレンダーUIの作り込み（テーブル組みで十分）

## 完了の定義

- 2ユーザーで予約→片方が重複予約を試みて弾かれる→変更→キャンセル、が通ること
- 並行リクエストのテストで排他が保証されていること
- タイムゾーンを切り替えて表示が正しく変わること
- リマインダーが時刻どおりに記録されること

## 評価チェックリスト

- [ ] トランザクション・ロックのAPIは明示的で理解しやすかったか
- [ ] 排他制約をマイグレーションで表現できたか（生SQLに逃げたか）
- [ ] 並行テストは書きやすかったか（テスト基盤の質）
- [ ] 日付・タイムゾーン処理は標準機能/定番ライブラリで完結したか
- [ ] 状態遷移（confirmed→canceled）と遷移条件をどの層に書いたか。フレームワークに置き場所の指針はあったか
- [ ] バックグラウンドジョブは組み込みか、外部依存が何個増えたか
- [ ] 「30分前ルール」のようなドメインルールの置き場所は自然に決まったか
- [ ] バリデーションエラーとHTTPステータスの対応付けは素直だったか

# 題材3: リアルタイムクイズ（フロントエンド深掘り用）

## 目的

Kahoot風の早押しクイズを題材に、状態機械・リアルタイム同期・時間駆動の更新・リアクティビティの粒度という、フロントエンドフレームワークの核心を測る。

## サーバーについて

サーバー側の学習は目的外。以下のいずれかで済ませ、**一度作ったら全フレームワークで使い回す**:

- 小さなWebSocketサーバー（Node + ws 等で100〜200行程度）を1回だけ書いて再利用する
- 試すフレームワークがフルスタック系（SvelteKit, Next.js等）でリアルタイム機能を持つなら、あえてそちらで実装してその機能を評価してもよい

サーバーの責務: ルーム管理、参加者管理、ゲーム状態の保持と遷移、全クライアントへの状態ブロードキャスト。クライアントは「イベントを送る」「状態を受け取って描画する」に徹する。

## ロールと画面

- **ホスト**: PCの大画面想定。ルームを作り、ゲームを進行し、問題と集計結果を表示する
- **参加者**: スマホ想定。ルームコードで参加し、回答ボタンを押す

問題データはハードコードされたJSON（4択×5問）でよい。問題作成UIは作らない。

## ゲームの状態機械

ゲーム全体が以下の状態を遷移する。**この状態機械をクライアント側でどう表現するかが、この題材の心臓部**。

```
lobby → question(n) → reveal(n) → (次の問題があれば question(n+1) へ) → podium
```

- **lobby**: ホストがルーム作成。4文字のルームコードが発行される。参加者はコード＋ニックネームで入室。ホスト画面に参加者一覧がリアルタイムで増えていく。ホストが「開始」で question(1) へ
- **question(n)**: ホスト画面に問題文と4択。参加者画面には色付きの回答ボタン4つのみ（問題文はホスト画面を見る建付け）。制限時間20秒のカウントダウンが全クライアントで表示される。参加者が回答すると自分の画面は「回答済み」表示に固定。ホスト画面には回答済み人数がリアルタイムで増える。全員回答 or 時間切れで reveal(n) へ自動遷移
- **reveal(n)**: 正解の発表。選択肢ごとの回答数を棒グラフで表示（アニメーション付き）。参加者画面には自分の正誤と獲得ポイント、現在順位。ホストが「次へ」で次の問題 or podium へ
- **podium**: 最終結果。上位3名を表彰台風に、順にアニメーションで表示。全参加者のランキング一覧も出す

## 機能仕様の要点

### スコアリング

- 正解で基礎1000点＋残り時間に比例したボーナス（速いほど高得点）
- 計算はサーバー側。クライアントは表示のみ

### カウントダウンタイマー

- サーバーが締切時刻を配り、各クライアントが自前でカウントダウン描画する（毎秒サーバーから送らない）
- 残り5秒で色が変わる等、時間による表示分岐を1つ入れる
- **見るポイント**: タイマーの開始・破棄のライフサイクル管理。コンポーネントのアンマウントや状態遷移でタイマーが確実に片付くか。ここが `useEffect` 地獄になるか、素直に書けるかはフレームワークで差が出る

### 切断への耐性

- 参加者がリロードしても、ルームコード＋ニックネームで復帰でき、スコアが維持される（サーバー側で保持し、再接続時に現在状態を送る）
- ホスト切断は考慮しない（ルーム消滅でよい）

### アニメーション

必ず実装する2箇所。フレームワークのトランジション機能（Svelte transition, Vue Transition, React系なら選定したライブラリ）を使うこと:

1. reveal画面の棒グラフが0から伸びる
2. podiumで3位→2位→1位の順に出現する

### 同一状態・複数ビュー

question状態のとき、ホストと参加者は同じゲーム状態から全く異なるUIを描画する。状態→ビューの写像をどう構造化するか（コンポーネント分割、条件分岐、ルーティング）を意識して設計する。

## クライアント状態の型（参考）

```
GameState =
  | { phase: "lobby", players: Player[] }
  | { phase: "question", index, question, deadline, answeredCount }
  | { phase: "reveal", index, correctChoice, counts[4], myResult?, ranking }
  | { phase: "podium", ranking }
```

判別可能ユニオン等で「不正な状態を型で表現できなくする」ことを試みる。型システムとの相性も評価対象。

## やらないこと

- 問題作成・編集UI
- 認証（ニックネームのみ）
- 複数ルームの同時進行の作り込み（動けばよい）
- 音声・効果音
- ネットワーク断の高度なハンドリング（自動再接続リトライ等。手動リロード復帰まで）

## 完了の定義

ホスト1画面＋参加者2画面（ブラウザ2窓）で、入室→5問プレイ→表彰台、が通ること。途中で参加者1人がリロードして復帰できること。

## 評価チェックリスト

- [ ] 状態機械の表現は素直だったか（状態管理ライブラリが必要になったか、組み込みで足りたか）
- [ ] WebSocket/SSEの購読とクリーンアップはライフサイクルに自然に載ったか
- [ ] タイマー処理でリソースリークの不安なく書けたか
- [ ] 回答済み人数のような高頻度更新で、再レンダリングの範囲は制御できたか（リアクティビティの粒度）
- [ ] トランジション/アニメーションは組み込み機能で書けたか、ライブラリ選定が必要だったか
- [ ] 判別可能ユニオンによる状態の型付けと、テンプレート/JSXでの絞り込みは快適だったか
- [ ] ホスト/参加者のビュー分岐はコンポーネント構造として綺麗に収まったか
- [ ] 開発体験（HMRで状態が保持されるか、devtoolsの質）はどうだったか

# 付録: 比較メモの残し方

フレームワークごとに1ファイル、以下の形式でメモを残すと後で比較しやすい:

```
# <フレームワーク名> <バージョン> (試用日)

## 実施した題材と所要時間
## チェックリスト結果（上記のコピー）
## 感動した点 / 苦しんだ点（各3つまで）
## このフレームワークを選ぶべき場面 / 避けるべき場面
## 生成AIとの相性（ドキュメント・エコシステムの学習しやすさ）
```
